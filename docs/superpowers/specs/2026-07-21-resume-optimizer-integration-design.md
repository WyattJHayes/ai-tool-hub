# AI 简历优化完整并入 Next.js 设计

## 状态与背景

本设计于 2026-07-21 经用户逐段批准，定义“AI 简历优化”从旧静态客户端和 Express
服务完整迁入当前 Next.js 生产应用的范围、架构、交互、数据迁移与上线标准。

当前生产流量由 Next.js 承接，但 Next 导航和生产工具数据缺少简历优化入口；旧客户端依赖
`/api/v1/auth/*`、`/api/v1/resume/*` 和 `/api/v1/payment/*`，对应的旧服务已被现行部署脚本
停用。因此，仅恢复工具卡片不能恢复功能，必须同时迁移客户端、认证、AI 接口、配额和支付。

本设计继续遵循以下已批准规范：

- `docs/superpowers/specs/2026-07-19-task-first-decision-matrix-design.md`
- `docs/superpowers/specs/2026-07-20-precision-instrument-console-design.md`

发生冲突时，本规范只覆盖简历优化功能、入口、相关 API、数据模型和迁移流程。共享导航、
主题令牌和基础组件继续以“精密仪器控制台”规范为准。

## 目标

- 在正式地址 `/resume/` 完整恢复简历编辑、文件导入、实时预览和 PDF 导出。
- 复用当前 Supabase 登录，不再维护第二套 JWT、Cookie 或用户密码。
- 恢复简历解析、JD 分析和轻度、中度、深度三级 AI 优化。
- 沿用旧系统当前有效的免费、基础会员、永久 VIP、配额和价格规则。
- 使用现有 XDDPAY 生产渠道完成下单、支付确认、会员激活和订单查询。
- 完整迁移旧用户、有效会员、剩余额度、历史订单和支付记录。
- 默认不在服务端持久化简历正文、JD 正文或 AI 输出。
- 恢复首页工具卡片、桌面导航和移动端菜单中的明显入口。
- 修复搜索结果中无文本匹配的热门工具被错误返回的问题。

## 非目标

- 不提供简历正文的服务端存储、自动云同步或跨设备编辑。
- 不增加团队协作、公开简历链接、版本历史、招聘方工作台或多语言功能。
- 不同时接入新的支付宝或微信直连渠道；本期只使用已选择的 XDDPAY 渠道。
- 不重构与入口、搜索、认证共享能力无关的工具目录功能。
- 不延续旧系统自建 JWT 认证和 `quota.json` 文件持久化。
- 不通过 iframe 或独立子域继续托管旧应用。

## 方案选择

### 方案 A：Next.js 原生整合（采用）

将旧功能按职责迁为 Next 页面、React 组件、客户端领域模块和 Route Handlers。认证统一使用
Supabase，配额和订单统一写入 Postgres。该方案初始迁移量最大，但路由、视觉、登录、部署、
监控和长期维护均只有一套，是唯一能完整消除当前断层的方案。

### 方案 B：静态客户端适配

把旧构建产物放入 Next `public`，只改 API 客户端和视觉外壳。它能较快恢复页面，但会继续
保留全局脚本、DOM 直接操作、重复认证状态和割裂的响应式体验，后续功能迭代成本高。

### 方案 C：恢复独立简历服务

重新启用旧容器，通过 Nginx 将 `/resume/` 和 `/api/v1/resume/*` 代理给独立服务。它对旧代码
改动最少，但会恢复双认证、文件配额和额外生产服务，与当前部署收敛方向冲突。

用户已选择方案 A，并要求完整恢复全部能力。

## 总体架构

### 页面与模块边界

- `app/resume/page.tsx` 提供 `/resume/` 页面入口和服务端页面框架。
- 简历编辑器使用独立的客户端工作区组件，负责编辑状态、自动保存、导入、预览和 AI 结果应用。
- 表单、预览、导入、AI 优化、账户配额和支付分别为独立模块，通过类型化数据和回调通信。
- 简历领域模型作为唯一数据源；表单和预览不得各自维护一份可漂移的数据副本。
- 旧客户端中可验证的文本提取、字段标准化、模板和分页逻辑可以迁移，但不得继续依赖
  `window` 全局对象、内联事件或旧 `apiClient`。

### 认证边界

- 所有受保护接口只接受当前 Supabase 会话。
- 客户端通过 Supabase SDK 取得会话；服务端验证访问令牌并以 `auth.users.id` 作为唯一用户 ID。
- 页面可以匿名编辑、预览、在本地保存和导出；AI 解析、JD 分析、AI 优化、配额和支付要求登录。
- 未登录用户触发受保护操作时打开现有登录界面，登录成功后恢复原操作上下文。
- 不迁移旧密码哈希，不接受旧 JWT，也不创建第二套认证 Cookie。

### API 边界

新接口使用当前 Next API 命名方式，不保留旧 `/api/v1` 前缀：

| 方法与路径 | 责任 | 登录 |
| --- | --- | --- |
| `POST /api/resume/parse` | 将简历文本解析为领域模型 | 是 |
| `POST /api/resume/analyze-jd` | 分析 JD 与关键词 | 是 |
| `POST /api/resume/optimize` | 以 SSE 返回三级优化进度与结果 | 是 |
| `GET /api/resume/quota` | 返回会员与可用额度 | 是 |
| `GET /api/resume/plans` | 返回可购买方案与渠道状态 | 否 |
| `POST /api/resume/orders` | 创建 XDDPAY 订单 | 是 |
| `GET /api/resume/orders` | 返回当前用户订单列表 | 是 |
| `GET /api/resume/orders/[id]` | 查询本人订单状态 | 是 |
| `POST /api/resume/payments/xddpay/notify` | 验签并履约支付事件 | 否，渠道验签 |

所有 JSON 错误统一返回稳定错误码、用户可读消息和请求 ID。SSE 使用 `progress`、`token`、
`done`、`error` 四类事件；`done` 包含最终结构化结果和更新后的配额。

## 简历领域模型与本地保存

领域模型至少包含：个人信息、求职目标、个人总结、工作经历、项目经历、教育经历、技能、
证书或补充模块、模板 ID 和版式设置。重复模块中的每一项必须有稳定本地 ID，以支持排序、
复制、删除、差异比对和撤销。

- 默认使用版本化 localStorage 记录保存，不依赖登录。
- 存储键必须包含 schema 版本；升级时显式迁移，无法迁移时保留原数据备份并提示用户。
- 保存状态分为“未保存”“保存中”“已保存”和“保存失败”，状态变化不移动工具栏布局。
- 导入和 AI 结果先进入草稿或差异层，用户确认后才写入当前简历。
- 清空或覆盖整份简历前必须二次确认，并提供单步撤销。
- 服务端不提供简历文档表，也不把正文写入 Supabase。

## 页面与交互

### 信息架构

- 顶部工具栏包含返回、简历名称、保存状态、导入、模板切换、PDF 导出、配额和账户入口。
- 桌面端为左侧编辑、右侧 A4 实时预览；两个区域使用稳定网格轨道并可独立滚动。
- 移动端使用“编辑 / 预览”分段控件切换，底部固定当前场景的主要操作。
- 编辑模块支持折叠、排序、复制和删除；新增按钮位于对应模块末尾。
- 用户在编辑、导入失败、登录或支付过程中都不会丢失当前简历。

### AI 工作流

- AI 面板提供简历解析、JD 分析和轻度、中度、深度优化。
- 执行前显示任务、所需输入、预计扣减额度和当前剩余额度。
- 轻度优化可以不提供 JD；中度和深度优化必须提供 JD，与旧有效规则一致。
- 三级优化沿用旧系统的提示词意图和结果结构，但共享统一的安全校验与流式协议。
- 每次解析、JD 分析或任一级优化成功消耗 1 次额度；失败、中断或超时不消耗额度。
- 优化结果按字段展示原文和建议，支持单条接受、全部接受、拒绝和撤销。
- 流式内容只作过程反馈；在收到合法 `done` 结果前不得覆盖简历。

### 文件导入

- 支持 PDF、DOCX、TXT、HTML 和 Markdown，单文件上限沿用旧系统的 10 MB。
- `.doc` 明确提示另存为 `.docx`；扫描件或无可提取文本的 PDF 给出可执行提示。
- 文件读取与初步文本提取在浏览器完成；登录后可调用 AI 结构化解析。
- AI 解析失败时回退到本地规则解析，并明确标记结果需要人工核对。
- 导入预览确认后才替换或合并当前简历，失败时不改变原内容。

### 实时预览与 PDF

- 表单更新驱动同一领域模型的 A4 预览，不通过 HTML 字符串复制状态。
- 模板只控制排版和语义令牌，不改变字段内容。
- PDF 在浏览器端生成；导出前等待字体和预览稳定，并检查分页、内容溢出和空白页。
- 导出结果必须与预览保持相同字段顺序、可见模块和模板选择。

## 视觉设计

简历页属于已批准的“精密仪器控制台”系统：深色中性工作面、冷白文字、精确 1px 边线、
电蓝与青色交互状态，以及橙色错误语义。不得使用灰绿体系。

- 科技感来自细网格布局、严格对齐、状态指示、数据化排版和克制的 140ms 状态过渡。
- 页面背景不得使用装饰性网格、渐变球、发光雾、玻璃拟态或持续扫描动画。
- 编辑区域是连续工作面，不将页面章节包装为层层嵌套的浮动卡片。
- 普通组件圆角不超过 6px，A4 预览保持纸张几何，不使用夸张圆角。
- 熟悉操作使用现有 Lucide 图标；图标按钮具有可访问名称和工具提示。
- 交互目标至少 44 x 44px，焦点、错误、选中和禁用状态不能只依赖颜色。
- 支持至少 `1440x900`、`1024x768`、`390x844` 和 `320x844`，无横向滚动、遮挡或文字溢出。
- `prefers-reduced-motion: reduce` 下移除非必要动效。

## 入口与路由

- 正式地址为 `/resume/`。
- 桌面顶部导航和移动端菜单增加“简历优化”。
- 工具目录恢复 ID 95“AI 简历优化”，其站内链接指向 `/resume/`。
- 首页恢复可扫描到的工具卡片或工具行入口，不制作营销式 Hero。
- `/tools/resume-optimizer`、`/tools/resume-optimizer/` 及已公开的旧站内地址使用永久重定向到
  `/resume/`；查询参数在无安全风险时保留。
- 导航、工具数据和路由必须共享一个 canonical URL，避免再次产生入口漂移。

## 配额与会员规则

### 权益规则

- 免费用户使用生产环境 `DAILY_QUOTA` 配置的每日额度，并按 `Asia/Shanghai` 自然日重置。
- 基础会员沿用一次性 10 次额度、价格 9.9 元；额度耗尽后才允许再次购买基础会员。
- 永久 VIP 沿用 99 元和不限次规则，但仍记录成功用量流水。
- 基础会员升级永久 VIP 时保留历史已用额度和流水，不重复返还。
- 旧配置中计划展示值与实际 `DAILY_QUOTA` 默认值不一致；新系统以部署时解析出的生产运行配置
  为唯一来源，计划展示、接口校验和扣减函数必须读取同一配置。上线前的配置对账报告必须列出
  生效值，不能依赖旧代码中的冲突默认值。

### 扣减协议

- 每个计费请求先在数据库事务中预留 1 次额度，再调用 AI 服务。
- 事务锁定用户配额账户，校验会员状态和余额，写入唯一预留流水，再更新账户缓存值。
- 成功收到并验证最终结果后，将预留流水提交为 `consumed`。
- AI 失败、超时、连接中断或结果无效时，将同一流水改为 `refunded` 并原子返还。
- 客户端为每次动作生成幂等键；网络重试不得创建第二次扣减。
- 永久 VIP 的用量流水金额为 0，仍保留动作类型、状态、请求 ID 和时间。

## 数据模型

### `resume_quota_accounts`

每个 Supabase 用户一行，保存当前计划快照、当前可用额度或无限标记、免费日用量窗口、版本号和
更新时间。它用于快速读取和事务锁定，不替代不可变流水。

### `resume_usage_ledger`

保存 `user_id`、动作类型、幂等键、状态、额度变化、请求 ID、创建和结算时间。幂等键唯一；
用户只能读取自己的流水，只有服务端角色可以创建或结算。

### `resume_memberships`

保存会员历史而非仅当前快照，包括计划、状态、来源订单、激活时间、失效时间、历史总额度、
历史已用额度和迁移来源 ID。每个用户最多存在一条当前有效权益。

### `resume_orders`

保存站内订单号、用户、计划、支付渠道、以分为单位的应付金额、状态、渠道交易号、过期时间、
支付时间、履约时间和迁移来源 ID。金额使用整数，禁止浮点比较。

### `resume_payment_events`

保存渠道事件号、订单号、签名验证结果、事件类型、处理状态、接收时间和经过脱敏的必要载荷。
渠道事件号与订单号形成幂等约束；原始密钥、完整敏感载荷和简历内容不得入库。

### 访问控制

- 所有表启用 RLS。
- 用户只能读取自己的配额、会员、订单和用量记录。
- 用户不能直接写余额、会员、订单状态或支付事件。
- 计费事务、支付履约和迁移只通过服务端受控函数或服务端角色执行。

## XDDPAY 支付

- 使用现有生产 `XDDPAY_APP_ID` 和 `XDDPAY_SECRET`，通过独立支付适配器隔离渠道字段。
- 创建订单时由服务端读取计划和金额，客户端提交的价格不参与计算。
- 回调先验签，再校验应用 ID、订单号、渠道交易号、金额、币种和可接受状态。
- 验签与字段校验通过后，在单个数据库事务中锁定订单、写入支付事件、标记已支付、激活权益并
  标记已履约。
- 重复回调对已履约订单返回渠道要求的成功响应，但不得重复增加额度或会员。
- 同一渠道交易号不能履约多个订单；金额或用户归属不一致时拒绝履约并触发告警。
- 订单查询只允许订单所有者；待支付订单超时后标为 `expired`，支付晚到时进入人工核对状态。
- 用户关闭支付页、网络断开或回调延迟时保留订单，并允许从账户抽屉重新查询。

## 旧数据迁移

### 数据范围

迁移旧 `quota.json` 中的用户、每日使用记录、会员和订单，以及服务器上可验证的支付记录。
迁移前对源文件和相关备份做只读快照并记录校验和。

### 用户映射

- 以规范化邮箱匹配 Supabase 用户，生成不可变的旧用户 ID 到 Supabase UUID 映射表。
- 已存在 Supabase 用户直接映射；不存在的旧用户创建待激活账户或使用 Supabase 支持的安全邀请
  流程，不能导入旧密码哈希。
- 邮箱冲突、无效邮箱或多对一匹配进入人工核对清单，不自动合并、不静默丢弃。

### 余额与订单

- 有效基础会员按 `totalQuota - usedQuota` 迁移剩余额度，并保留总额、已用额和来源记录。
- 有效永久 VIP 迁移为永久权益；无效或未知状态保留历史但不激活。
- 每个旧订单保留原订单号、状态、金额、支付方式、交易号和时间；映射到新的站内 ID。
- 已履约订单不会在迁移过程中再次发放权益。
- 旧每日用量按原日期导入流水；当前自然日用量同步到配额账户。

### 迁移执行

- 迁移工具必须支持 `dry-run`、正式执行、断点续跑和重复执行。
- 所有导入行以来源类型和来源 ID 建立唯一约束。
- 预演和正式迁移均输出用户数、有效会员数、各类剩余额度总和、各状态订单数、金额总和、
  未匹配数和错误数。
- 切流前源数据进入只读窗口；正式迁移后执行逐项对账，差异未归零不得开放付费与 AI 入口。
- 旧数据和对账产物按受限备份保存，不进入仓库。

## 隐私与安全

- 简历正文、JD 正文和 AI 输出只存在于浏览器状态和单次服务端请求内存中。
- 服务端完成请求或连接结束后立即释放正文，不写数据库、应用日志、错误上报或分析事件。
- 日志只记录请求 ID、匿名化用户 ID、动作、模型、耗时、状态、额度流水 ID 和 token 用量。
- 上传文件默认不离开浏览器；仅提取出的文本在用户主动执行 AI 解析时发送。
- 接口校验内容长度、MIME 类型、扩展名、结构和请求频率；错误消息不得回显敏感正文。
- 支付密钥和 Supabase 服务端密钥只存在于服务器环境变量，不暴露在 `NEXT_PUBLIC_*` 中。
- AI 提示词明确将简历和 JD 视为不可信数据，防止其中内容覆盖系统指令。

## 异常处理

- 导入失败保留当前简历，并按格式、大小、扫描件或解析失败提供明确恢复操作。
- AI 请求未登录返回认证错误；额度不足返回当前计划、剩余额度和可购买方案入口。
- SSE 中断时保留已经显示的过程文本，但标记为未完成且不可一键应用，额度自动退还。
- AI 完成但结构校验失败时视为失败，不覆盖简历并退还额度。
- 本地保存失败时保留内存状态并提示导出备份，不假装已保存。
- PDF 分页检查失败时阻止下载并定位溢出模块；用户可切换模板或调整内容后重试。
- 支付创建失败不产生可履约订单；回调失败记录安全事件并允许渠道重试。
- 回调延迟显示“待确认”，不显示支付失败；用户可查询状态而不重复下单。

## 搜索修复

`/api/search` 必须先确认名称、描述、分类、场景或标签存在文本匹配，再对匹配集合应用热门状态
加权。`status === 'hot'` 只能改变相关结果排序，不能让零文本匹配工具进入结果。简历优化工具
恢复到生产数据后，搜索“简历”“简历优化”和其有效标签应返回该工具。
